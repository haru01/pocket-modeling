# 用語ガイド（ポイント解説辞書）

ファシリテーション中、DDD／EventStorming の専門用語が**初めて登場した時**に AI がここから 1 行解説を引いて「💡」アイコン付きで添える。既出の用語は繰り返さない（出力節約原則）。

## 使い方（AI 向け）

- セッション内で「初出か既出か」を判定する基準は **チャット履歴のテキスト検索**
- 1 行解説は「**用語名（英語）＝ 1 文の平易な日本語 ＋ 当該ドメインからの具体例**」の形に揃える。具体例は今回のセッションで出ている言葉（例: `Event` `Participation`）を必ず使う
- 解説は**簡潔に**。背景・歴史・対比論点は省略。深掘りはユーザーが「もっと教えて」と聞いたときのみ
- フェーズ完了テンプレでは「### 💡 ポイント解説」セクションで初出分だけまとめて報告 → 会話の流れの中で「実際に説明したもの」がチャットログに残る形になる

## 用語辞書

### EventStorming の付箋色

| 用語 | 1 行解説 |
|---|---|
| **ドメインイベント / Event（🟧 オレンジ）** | 業務的に「あ、これが起きた」と言える過去の出来事。「〜された」「〜完了した」と書く。例: 「注文が確定した」「在庫が減った」 |
| **コマンド / Command（🟦 青）** | 「これをやってほしい」とシステムへの依頼。命令形で書く。例: 「注文する」「在庫を引き当てる」 |
| **アクター / Actor（🟨 黄）** | コマンドを発行する主体。人間（顧客・担当者）／システム自動／AI／外部 API など |
| **集約 / Aggregate（🟫 茶 or 黄）** | 「同時に変わるデータの塊」。トランザクション境界。例: 注文 1 件と注文明細は同じ集約 |
| **ポリシー / Policy（🟪 紫）** | 「あるイベントが起きたら、次にこのコマンドを発行する」という業務ルール。例: 「注文確定 → 在庫引き当て」 |
| **リードモデル / Read Model（🟩 緑）** | 画面表示や判断材料のために「読むだけ」のデータ。書き換えはしない。例: ダッシュボード、検索一覧 |
| **ホットスポット / Hotspot（🟥 赤）** | 設計判断に迷う点・対立がある点。即決せず `[?]` でマークして残す |
| **節目イベント / Pivotal Event（⭐）** | タイムラインを大きく区切る出来事。その前後で業務の関心事・登場人物・言葉が変わる。例: 「注文が確定した」を境に販売の話から物流の話に変わる |

### DDD の境界・コンテキスト

| 用語 | 1 行解説 |
|---|---|
| **境界付きコンテキスト / Bounded Context（BC）** | 「同じ言葉が同じ意味で通じる範囲」。例: 営業の「顧客」と請求の「顧客」は別 BC のことが多い |
| **ユビキタス言語 / Ubiquitous Language** | その BC 内で全員（業務・開発・AI）が同じ意味で使う言葉。`contexts[].lang` がこれ |
| **上流 / Upstream（up）** | 自分が**参照する側**の BC（自分は下流）。API を呼ぶ・モデルを借りる側ではなく、提供される側 |
| **下流 / Downstream（dn）** | 自分が**提供する側**の BC（相手が下流）。API を呼ばれる側 |
| **Customer-Supplier** | 下流が上流に「こういう API がほしい」と注文できる関係。優先順位を交渉できる |
| **Conformist** | 下流が上流の形にそのまま従う関係。交渉力なし（例: 外部 SaaS の言葉に合わせる） |
| **ACL（Anti-Corruption Layer）** | 下流側に変換レイヤを挟んで、上流の汚れた言葉を自分の言葉に翻訳して隔離する |
| **Shared-Kernel** | 両 BC で共有する小さなモデル。変更は両方の合意が必要 |

### サブドメイン分類（コアドメイン蒸留）

| 用語 | 1 行解説 |
|---|---|
| **コアドメイン / Core Subdomain** | 間違えると事業が成り立たない・競合との差別化そのものの領域。モデリングと実装に最も投資する。例: 買取サービスなら「査定額の算定」 |
| **サポートサブドメイン / Supporting Subdomain** | 業務に必要だが差別化ではない領域。ほどほどの作り込みで良い。例: 会員管理・予約枠の管理 |
| **汎用サブドメイン / Generic Subdomain** | 買ってくれば済む・他社の真似で十分な領域。SaaS やライブラリで済ませる。例: 決済・メール送信・認証 |
| **コアドメイン蒸留 / Distillation** | 全部を同じ熱量で作らないために、CORE / SUPPORTING / GENERIC を仕分けて投資配分を決めること |

### トランザクションと整合性

| 用語 | 1 行解説 |
|---|---|
| **SAME-TX（同一トランザクション）** | 1 つの DB トランザクション内で完結する処理。`brs[]`（分岐）で書く。即時整合 |
| **EVENTUAL-TX（結果整合）** | イベント発火 → 別トランザクションで後処理。`policies[]` で書く。多少遅れて整合する |
| **不変条件 / Invariant（RULE）** | 集約が**常に**守るべき業務ルール。違反したら集約が壊れる。例: 「在庫数は 0 以上」 |
| **エラー / ERR** | 不変条件違反や前提条件未充足で起きる業務エラー。例: `OutOfStock`（在庫不足） |

### 意思決定（フェーズ 6）

| 用語 | 1 行解説 |
|---|---|
| **意思決定ログ / decisions[]** | 設計の分岐点で「採用案 / 不採用案 / 各案の理由」を残す記録。**未来の自分・実装者・後から参加するメンバー**が「なぜそうなっているか」を再現できるようにする |
| **why（採用理由）** | その案を採用すると業務がどう良くなるか。「整合性管理コストが低い」「ユーザー導線が直感的」など、**業務文脈**で書く |
| **why_not（不採用理由）** | その案を捨てた業務上の理由。「責務逸脱」「整合性管理が破綻する」など。**好み**ではなく**業務的な不利益**で書く |
| **affects** | この意思決定が影響を及ぼす集約・BC のリスト |

## ポイント解説の書き方（標準形）

1 行目は **日常の業務の言葉** で言い切る（他の DDD/専門用語に依存しない）。2 行目は今回のドメインから **「⚪️が起きたら△△する」** の形の具体例を 1 つ。

| | NG: 専門用語で専門用語を説明 | OK: 業務語で言い切る |
|---|---|---|
| POLICY | POLICY ＝ EVENTUAL-TX を表す反応 | POLICY ＝ ある出来事が起きたら自動で次の処理が走るという約束事 |
| BC | BC ＝ Ubiquitous Language の境界 | BC ＝ 同じ言葉が同じ意味で通じる範囲。ここを越えると意味が変わる |
| EVENTUAL-TX | EVENTUAL-TX ＝ Saga による補償付き分散 TX | EVENTUAL-TX ＝ 別々の処理が後から追いついて整合する形（即時ではない） |
| ACL | ACL ＝ Conformist を避けるための変換層 | ACL ＝ 外部システムの言葉を自社の言葉に翻訳する仕切り |

**1 ターンに 1〜2 用語まで**。3 つ以上重なるときは、今のその問いに直結する 1 つだけに絞る。残りは次のターン以降で。

## 噛み砕きパターン（ユーザーが「もっとわかりやすく／？」と求めたとき）

抽象定義を繰り返さない。以下のいずれかの形で **再** 説明する。

### パターン A: ビフォー / アフター対比表

> 「この用語があるとき／ないとき、業務がどう違うか」を 2 列で並べる

| | この概念 **なし** | この概念 **あり** |
|---|---|---|
| 例: POLICY | 注文確定後に在庫を引き当てるロジックを各画面が抱える | 「注文確定 → 在庫引き当て」を 1 か所に集約・後から変更が容易 |

### パターン B: 「2 つの仕事が混ざっている」分解

> 1 つの曖昧な概念を「実は別々の仕事」として分解して示す

```
仕事 A: <一方の責務>（例: 外部 API から価格を取ってくる）
仕事 B: <もう一方の責務>（例: 取れた価格を画面に並べる）
→ どちらの BC の話か、を切り分ける
```

### パターン C: 「お金になるか／意思決定を駆動するか」基準

> 業務イベントかどうかの判定で使う。「これが起きた後に **別の業務が走るか／お金が動くか／別の人が見るか**」で線を引く

### パターン D: 比喩

> 業務の比喩で言い換える。例: 「POLICY ＝ 給湯器のサーモスタットみたいなもの。温度が下がったら自動で点火する設定」

**ルール**: 噛み砕きは必ず **今回のドメインの単語** を 1 つは入れる（例題のままの汎用説明にしない）。

## 「良い説明」と「わかりにくい説明」の例

意思決定の `why`/`why_not` を書くときの目安：

| 観点 | わかりにくい例 | わかりやすい例（業務文脈で再現できる） |
|---|---|---|
| 採用理由 | 「DDD 的に正しい」 | 「capacity は公開時に確定する属性で、申込ごとに再計算する必要がないため、Event 集約に持たせると整合性管理が楽」 |
| 不採用理由 | 「責務違反」 | 「Participation 集約に capacity を持たせると、申込のたびに他の Participation を全部読んで合計しないと残席が出せず、ロック競合が頻発する」 |
| 制約の書き方 | 「セキュアに保管する」 | 「個人情報保護法に基づきメールアドレスは AES-256 で保管する」 |
| 集約の目的 | 「ユーザー情報を管理する」 | 「メンバーシップ状態（有効・休止・退会）の単一の責任主体。課金・通知の前提となる」 |

**判定の目安**: 「この `why` を後から読んだ人が、自分でコードレビューに反映できるか」。できないなら抽象的すぎる。

## どこに記録されるか

| 何を | どこに |
|---|---|
| 用語の 1 行解説（初出時） | チャット本文「### 💡 ポイント解説」（フェーズ完了テンプレに含まれる） |
| BC 固有の語彙（英日辞書） | `contexts[].lang.aggs/cmds/evts/...`（DML） |
| 集約の目的・背景・制約（業務文脈で再現できる粒度で） | `aggregates[].purpose/background/constraints`（DML） |
| 意思決定の採用/不採用理由（業務文脈で再現できる粒度で） | `decisions[].options[].why/why_not`（DML） |
| ストーリー散文（業務を時系列で追える流れ） | `narratives[].prose`（DML） |

DML 側に書いた `why`/`why_not`・`purpose` は HTML §5（意思決定ログ）・§7（集約候補）に描画されるため、**チャットを読まなくても HTML だけで後から参加した人がキャッチアップできる**状態を目指す。
