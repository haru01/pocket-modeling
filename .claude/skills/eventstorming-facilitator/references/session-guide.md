# 90分ファシリテーションガイド

> **v5（YAML-only / dmlctl 運用）**: 各フェーズの「書き戻し先」は `.dml.yaml` の
> トップレベルフィールド。本文書中の「`.md` を書く」記述は対応する DML フィールド
> （`narratives` / `actions` / `questions` / `queries` / `contexts[].description` 等）
> への書き込みと読み替える。
>
> **本書と SKILL.md ワークフローの対応**: 本書は SKILL.md の 9 フェーズワークフローを
> 90 分セッション用に短縮したファシリテーション質問集。区切りと SKILL.md フェーズの対応：
>
> | 本書の区切り | SKILL.md フェーズ |
> |---|---|
> | 0〜10 分 フレーミング | フェーズ 1 (スコープ確認) + フェーズ 2 (ストーリー) |
> | 10〜40 分 イベント収集 | フェーズ 3 (イベント発見) |
> | 40〜65 分 CMD/POLICY マッピング | フェーズ 4 (CMD→EVT→POLICY チェーン) + フェーズ 4.5 (BC 境界) |
> | 65〜80 分 コンテキストと集約の導出 | フェーズ 4.6 (目的・背景・制約) + フェーズ 5 (不変条件・属性) |
> | 80〜88 分 集約属性と意思決定 | フェーズ 5 続き + フェーズ 6 (意思決定ログ) |
> | 88〜90 分 クローズ | フェーズ 7 (整合性チェック・確定版) |
>
> 完全な 9 フェーズ進行（時間制約なし）は `SKILL.md` のワークフロー節を参照。

## 0〜10分：フレーミング

以下の3問のみで確認する（余分な質問は加えない）：

```
1. 対象フローは？（例：「登録〜内定」「求人掲載〜採用」「全体」）
2. 主要アクター視点は？（ユーザー / 企業 / 両方）
3. ゴールは？（全体像把握 / マイクロサービス分割 / 要件整理 / その他）
```

ドメイン固有の特性も確認するとよい：
- AIエージェントや自動バッチ処理はあるか？
- 外部システム連携（メール・カレンダー・決済など）はあるか？

## 10〜40分：イベント収集（提示→確認スタイル）

**やること**: 候補リストを先に提示し、ユーザーに確認・修正させる。「どんなイベントがありますか？」とは聞かない。

### 手順

1. `references/domain-starters.md` を参照してドメインに近いスターターを選ぶ
2. 10〜20件の候補イベントをフェーズ別に下書きして提示する

```
─── 〇〇フェーズ ───
[1] 〇〇が完了した
[2] 〇〇が登録された
...
─── △△フェーズ ───
[3] 〇〇が実行された
...
```

3. ユーザーに確認：「このタイムラインに**抜けているイベント**はありますか？修正点は？」
4. 追加・修正を反映 → 合意が取れたら次フェーズへ

### イベント記述ルール
- 過去形・受動態で記述する（例：「〇〇が完了した」「〇〇が通知された」）
- 粒度は「運用上意味のある中粒度」（大きすぎず・細かすぎず）
- 不明点は `[#question]` タグで明示し、推測しない

## 40〜65分：コマンド / ポリシー / アクター マッピング

各イベントに対して以下を特定する：

| 確認項目 | 質問例 |
|---|---|
| コマンド | 「このイベントを引き起こしたコマンド（操作）は？」 |
| アクター | 「誰が・何がそのコマンドを実行した？」 |
| ポリシー | 「どんなルール・条件でそのコマンドが実行されましたか？」 |

**アクター種別を必ず確認する：**
- 人間（求職者・企業担当者・管理者など）
- システム自動（イベントトリガーで自動実行）
- AIエージェント（チャット・推薦・日程調整など）
- スケジューラー（バッチ・定期実行）
- 外部システム（メール・決済・カレンダーなど）

テーブル形式で全体を一括提示し、1ラウンドで確認・修正を求める。

### インフラ系ドメインの BC 昇格判定（通知・スケジューラ・決済・メール等）

通知・バッチ・外部 API 連携が登場したら、**その場で「BC 昇格 vs POLICY 留置」を判定する**。
判定基準は `references/dml-spec.md` の「インフラ系ドメインの扱い」節を参照：

- 通知種類が 1 種類のみ / 状態を持たない → POLICY 留置
- 通知種類が複数 / SENT/FAILED 等の状態を持つ / 監査ログ兼用 → BC 昇格

判定を保留する場合は `[?]` でホットスポットに残す。
**「データモデルはあるが BC 宣言がない」宙吊り状態を避ける**のが本ステップの目的。

## 65〜80分：コンテキストと集約の導出

### 境界付きコンテキスト候補の見つけ方
- 言語（用語の意味）が変わる境界に注目する
- 責務（誰が何を所有するか）が変わる境界に注目する
- イベントクラスターをグループ化して名前をつける

### BC 間依存方向の導出（必須）

各 BC ペアについて以下を 1:1 で決定する：

1. **どちらがどちらを参照するか**（Command 内や Repository から見て、どの BC のモデルをロード／参照するか）
2. **関係タイプは何か**
   - `Customer-Supplier`: 下流が上流の API/モデルを安定的に利用
   - `Conformist`: 下流が上流の形に従う（変換せず利用）
   - `Shared-Kernel`: 両 BC で共有するモデル部分
   - `ACL`（Anti-Corruption Layer）: 下流が上流を変換レイヤで隔離

決定結果を DML（YAML）の `contexts[].up` / `dn` に反映する（`rel` に関係タイプを併記。`references/dml-spec.md` 参照）。

### 集約候補の見つけ方
- 「一緒に変わるもの」をひとつの集約にする
- 不変条件（常に守られなければならないビジネスルール）を列挙する
- 集約の生成・変更・削除の条件を確認する

### 集約属性の DML 記述（必須）

集約候補が固まったら、不変条件を書き出す直前に **DML の `aggregates[].attrs[]` で属性を固める**：

- 各属性は `{ name, type, required, note }`（`name` は camelCase、`type` は `EventId` / `string` / `int` / `date` 等の自由文字列）
- Branded ID は `type: EventId` のような型名で参照する（実装側で別途定義）
- 列挙値は `type: string` + `note: "DRAFT / PUBLISHED / CANCELLED のいずれか"` のように補足する（`states[]` と一致させる）
- 不変条件は `scenarios[].rules[]`、エラーは `scenarios[].errs[]`、AGG が emit するイベントペイロードは `aggregates[].events[].params[]` に書く（`params[]` の構造は `attrs[]` と同じ）

属性を書くことで **抜け漏れ**（例: `format`・`startsAt`・`endsAt` などの基本フィールド欠落）を防ぐ。Zod ブロックを `.md` 側に書く慣習は廃止された（属性表は HTML §7 が `aggregates[].attrs[]` から自動描画する）。

## 80〜85分：集約の目的・背景・制約を言語化する（フェーズ 4.6）

属性で「形」を固めた直後、**不変条件（RULE）と例外（ERR）を引き出す前** に、各 AGG が「なぜこの単位で切り出されるか」を 3 つの問いで言語化する。RULE は制約の機械化、ERR は制約違反の表面化なので、その上流に「意図」を固めると不変条件が自然と出やすい。

各 AGG について 1 ターンずつ以下を確認し、**`.dml.yaml` の `aggregates[]` エントリ** に記録する（HTML §7 が自動描画する）：

| 問い | 質問例 | 出力先（DML） |
|---|---|---|
| **目的（必須・30字以上）** | 「この AGG が無いと業務はどう困るか？単一の責任主体として何のソース・オブ・トゥルースになるか？」 | `aggregates[].purpose`（1 文） |
| **背景（推奨）** | 「なぜ今この AGG を切り出すか？既存運用の何が痛い／重複していて、この AGG を入れると何が変わる？」 | `aggregates[].background`（1〜3 文） |
| **制約（推奨）** | 「業務／法令／プラットフォーム由来で守るべき非機能・ルールは？プラン制限・上限・SLA・規制は？」 | `aggregates[].constraints[]`（文字列リスト） |

**書き分けのコツ：**
- 「目的」は CMD で表現済みの **what** を書かない（「コミュニティを作成・削除する」は NG）。**why / どんな単位の責任か** を書く（「コミュニティの所有権と公開設定を管理する単一の責任主体」が OK）
- 「制約」は検証可能な形で。「セキュアに保管」より「個人情報保護法に基づきメールアドレスは AES-256 で暗号化保管」のほうが実装判断の材料になる

**BC レベルは任意：** `.md` §7 コンテキスト候補カードの `#### 目的` / `#### 背景` / `#### 制約` は任意。「BC 共通の戦略的判断」を 1 文で書ける場合のみ追加する。AGG レベルと重複する内容なら BC レベルは省略してよい。

**不足検知：** 全 AGG の `aggregates[].purpose` が 30 字以上書かれているか確認。空・短すぎる項目はホットスポット `H-WHY` 候補としてマークし、`references/quality-check.md` の S8 で再走時に検出される。

**DML への反映（必須）：** §5 で確定した AGG メタを `.dml.yaml` のトップレベル `aggregates[]` に追加する。各エントリは `name`（必須・PascalCase）・`ctx`（必須・所属 BC の `contexts[].name`）・`purpose`（必須）・`background`（推奨）・`constraints[]`（推奨）・`states`（推奨・upper-snake 配列）。AGG は所有 BC は 1 つ。同時に、所属 BC の `contexts[].aggs` には AGG 名（PascalCase 文字列）を**軽量名簿**として追加する（詳細を持たない）。

**推奨追加項目（フェーズ5でもよい）：**
- `aggregates[].transitions[]`: 1〜2 件、`from`/`to`/`via`（scenarios[].cmd と一致するトリガー CMD 名）／必要なら `when`
- `aggregates[].events[]`: AGG が emit する EVT を `name`／`params` で列挙
- `aggregates[].attrs[]`: ペイロード属性を `name`／`type`／`required`／`note` で

これにより quality-check / causal-check が以下の整合を検証できる：
- `scenarios[].agg` ⇔ `aggregates[].name`（孤立 AGG / 未定義 AGG 参照の検出）
- `scenarios[].cmd` ⇔ `aggregates[].transitions[].via`（CMD が AGG 状態遷移に紐付くか）
- `scenarios[].evt` ⇔ `aggregates[].events[].name`（EVT が AGG の宣言済み発火イベントか）
- `contexts[].aggs` 名簿 ⇔ `aggregates[].ctx`（双方向参照の整合）

## 85〜88分：意思決定ログのファシリテーション（フェーズ 6）

セッション中の `[?]` ホットスポットや、AGG/BC 配置で迷った判断のうち **「選択肢が複数見えている」もの** を `decisions[]` に昇格させる。これは設計判断の歴史を残し、後続の実装エージェントや次回セッションで「なぜそうなっているか」を引き継ぐためのログ。

### ファシリテーションの手順

1. **迷っている判断を見つけたら、選択肢を 2〜3 個出す**（「A 案 / B 案 / C 案」と並べる）
2. **各案について `why`（採用する理由）または `why_not`（採用しない理由）を一緒に言語化する**。業務文脈で書く（「整合性管理コストが高い」「責務逸脱」「申込導線が直感的」など）
3. **採用案を決めたら、`decisions[]` に記録する**：

   ```yaml
   decisions:
     - id: D1
       topic: 定員（capacity）はどの AGG が所有するか
       chosen: Event 集約に持たせる
       options:
         - name: Event 集約に持たせる
           adopted: true
           why: "公開時点で確定する属性で、Participation と独立に変更される"
         - name: Participation 集約に持たせる
           why_not: "個別申込ごとに上限を計算し直す必要があり、整合性管理コストが高い"
       affects: [Event]
   ```

4. **決められないときは `chosen: 未確定`** で保留する。`options[]` の理由だけは書いておく（後続で再評価する材料を残す）

### 決定の粒度

- AGG 配置・状態管理者（capacity 持ち主など）・正規化 vs 重複保持・BC 昇格 vs POLICY 留置・SAME-TX vs EVENTUAL-TX など、**「実装エージェントが Issue を読んだとき迷いそうな分岐点」** を優先的に書く
- 「メールテンプレートの文面」「DB のカラム名」のような **粒度が細かすぎる判断は書かない**（実装側の自由度を奪う）

### `why` / `why_not` の粒度（業務文脈で再現できる解像度）

**判定の目安：「この理由を後から読んだ人が、自分でコードレビューに反映できるか」**。できないなら抽象的すぎる。専門用語だけで終わらせず、**業務文脈の言葉**で書く。

| 観点 | わかりにくい | わかりやすい（業務文脈で再現できる） |
|---|---|---|
| 採用理由 | 「DDD 的に正しい」 | 「capacity は公開時に確定する属性で、申込ごとに再計算する必要がない。Event 集約に持たせると整合性管理が楽」 |
| 不採用理由 | 「責務違反」「不自然」 | 「Participation 集約に capacity を持たせると、申込のたびに他の Participation を全部読んで合計しないと残席が出せず、ロック競合が頻発する」 |

ファシリテーション中に抽象用語（「責務」「凝集」など）が出てきたら **「具体的にどう困りますか？」「業務でどんな不利益が出ますか？」と 1 段掘り下げて言葉にする**。掘り下げた答えを `why_not` に書く。

専門用語そのものが初出のときは AI が `references/term-glossary.md` から 1 行解説を引いてチャットに添える（毎ターンの行動 ① ポイント解説原則）。

### `chat-output-format.md` との連携

フェーズ完了テンプレ末尾の「### 追加された DML」ブロックに `decisions[]` 新規エントリも含める（採用/不採用理由を 1〜2 行ずつで簡潔に報告）。加えてフェーズ 6 完了時のみ「### この意思決定のポイント」セクションを出し、各 decision について **業務的な不利益で語る不採用案** と **業務的に何が楽になる採用案** を 1 文ずつ要約する（DML 側 `options[].why`/`why_not` にも同じ文を保存）。

## 85〜90分：クローズと次のアクション

### オープンクエスチョンのクローズ
- セッション中に蓄積した `[#question]` をすべて確認する
- 解決したものは `[CLOSED]` + 解決内容でマークする
- 残ったものはオーナーと優先度を記録する

### ドラフト確認（出力前の必須ステップ）
ファイル出力の前に、以下をまとめて提示してユーザーのOKをもらう：
- イベントリスト（フェーズ別）
- コマンド / ポリシー / アクター テーブル
- コンテキスト候補と集約候補
- 集約ごとの DML 属性（`aggregates[].attrs[]`）・イベントペイロード（`aggregates[].events[].params[]`）
- BC 間依存方向（UPSTREAM / DOWNSTREAM）
- DML `contexts[].lang` の日本語↔英語辞書（全フロー図ラベルが登録済みか確認）

「この内容でよければファイルを出力します」と確認する。

## インタビュースタイル

- 1ターンあたり3〜5問に絞る
- 候補を先に提示してユーザーに確認させる（開放型質問は避ける）
- 不確かな箇所は `[#question]` でマーク；推測・補完しない
- 不明な領域を過剰モデリングしない
