# チャット出力フォーマット仕様

> **v5（YAML-only / dmlctl 運用）**: `.md` は廃止。すべての書き込み対象は `.dml.yaml` の
> トップレベルフィールド。本文書中の「`.md` を Write/Edit」「§N に書く」記述は
> 「対応する DML フィールドを `dmlctl set/add/remove` で更新」と読み替える。
> 旧 MD セクション ↔ DML フィールドの対応は SKILL.md「DML トップレベル構成（v5）」を参照。

EventStorming セッション中の各ターンで、チャット本文に何をどの順で出すかを定義する。

Claude Code（CLI/PCアプリ/スマホアプリ）はインライン `<svg>` / Mermaid フェンス / 画像プロトコルを描画しないため、**チャット本文は Markdown のテキスト要素（テーブル・絵文字・コードフェンス）のみ**で構成する。詳細なフロー描画は HTML ファイルに書き出してブラウザに任せる。

---

## 1. 出力モードの2分類

| モード | いつ | 内容 |
|---|---|---|
| **フェーズ内往復** | フェーズが完了していない、細かい質問・修正・確認 | Markdown のみ・短く |
| **フェーズ完了** | フェーズの主要項目が確定 (ユーザー OK or 主要項目揃い) | Markdown + 構造化テーブル + DML 抜粋（`contexts` / `aggregates` / `scenarios` / `policies` の 4 リストから差分。`contexts[].lang` 追加識別子も含む） + HTMLパス案内 |

判定基準は §4。

---

## 2. フェーズ内往復のテンプレート

```markdown
<本文: ユーザーの応答への返答・確認・1つの問い。短く>

### 💡 ポイント解説 (このターン初出のみ)
- **<用語名>** ＝ <日常の業務の言葉で 1 文・他の専門用語を使わずに書く>
  例: <今回のドメインから「⚪️が起きたら△△する」など具体的に>

### ホットスポット (差分のみ)
- H{n}. [?] <設計判断>: <なぜ迷うか>

### 未確認事項 (差分のみ)
- Q{n}. <項目>: <確認したいこと>

> 迷ったら `？` を送ってください
```

ルール:
- **HTML 更新しない**（フェーズ完了まで保留）
- **DML 抜粋出さない**
- 💡 ポイント解説：DDD／EventStorming の専門用語が**そのターンで初出**したときだけ出す。辞書は `references/term-glossary.md`。既出は繰り返さない（出力節約原則・§10）
  - **書き方**: 1 行目は他の専門用語を使わない日常語で言い切る／2 行目は今回のドメインで「⚪️が起きたら△△する」形の具体例。**1 ターンに 1〜2 用語まで**
  - **「もっとわかりやすく／噛み砕いて／？」と求められたら**抽象定義をやめて、比喩・対比・小さな表で再説明する（noteパターン例: `references/term-glossary.md` §噛み砕きパターン）
- ホットスポット / 未確認事項は **新規・更新があったもののみ** を出す。変化なしならセクションごと省略
- 本文末尾に問い 1 つで終わる (複数質問はしない)
- 末尾の `?` シグナル案内は省略可 (毎ターン繰り返さなくていい。初回 + フェーズ完了時のみ)

## 3. フェーズ完了のテンプレート

```markdown
**フェーズ{N} 完了: {phase_name}** ✅

{1〜2文の要約。何が決まったか、どの SCENARIO/BC が追加されたか}

### Event Flow ({図のタイトル})

| レーン (BC) | 🟨 Actor | 🟦 Command | 🟪 Policy | 🟧 Event |
|---|---|---|---|---|
| **{BC名1}** | {Actor} | {Command} | {Policy} | {Event} ⚡ |
| **{BC名2}** | — | {Command} | {Policy} | {Event} ⚡ |
| **{BC名1}** | {Actor} | {Command} | — | {Event} |

⚡ = 次レーンへの非同期遷移

> 詳細描画: [eventstorming-YYYYMMDD-HHMM.html](dist/eventstorming/eventstorming-YYYYMMDD-HHMM.html) （ブラウザで自動更新）

### 追加された DML

\`\`\`dml
{該当フェーズで確定した contexts / aggregates / scenarios / policies のみ（YAML）。
トップレベル `aggregates[]` には AGG メタ（name/ctx/purpose/states 等）、`contexts[].aggs` には AGG 名（PascalCase 文字列）の名簿}
\`\`\`

### 新規ラベルの追加（DML `contexts[].lang` への追加分）

| 英語識別子 | 日本語ラベル | 所属 BC | 種別 |
|---|---|---|---|
| <EnId> | <jp> | <bc-slug> | <kind> |

### 💡 ポイント解説（このフェーズで初出のみ）
- **<用語名>** ＝ <日常の業務の言葉で 1 文・他の専門用語を使わずに書く>
  例: <今回のドメインから「⚪️が起きたら△△する」など具体的に>

### この意思決定のポイント（フェーズ6完了時のみ）
- **D{id} {topic}** — 採用は「{chosen}」。理由を 1 文で：<業務文脈で再現できる説明>
- **もし不採用案を選んだら何が困るか**：<業務的な不利益を 1 文>

### ホットスポット
- H{n}. [?] <設計判断>: <理由>

### 未確認事項
- Q{n}. <項目>: <確認内容>

---

**次のフェーズ: {next_phase_name}**

ここで問いです。

{次フェーズの問い 1 つ}

> 迷ったら `？` を送ってください
```

ルール:
- **HTML ファイルは Write/Edit で更新** し、チャット本文にはパスのみ案内
- 代替シナリオがある場合は、テーブル形式のフローを **複数並べる** (ハッピーパス + 代替1 + 代替2)
- DML 抜粋は §4 の粒度ルールに従う
- 新規ラベル（`contexts[].lang` 追加分）は **新規追加分のみ**。既出の識別子は出さない
- 表内の付箋ラベルは記号を付けず日本語ラベルそのままで書く。種別は表ヘッダーの絵文字＋カラム名で識別
- 💡 ポイント解説：そのフェーズで**初出**した DDD／EventStorming 用語のみ。辞書は `references/term-glossary.md`。なければセクションごと省略
  - **書き方**: 1 行目は他の専門用語に依存しない日常の業務語／2 行目はそのドメインの具体例（「⚪️が起きたら△△する」形）。**1 フェーズあたり 1〜2 用語**まで。3 つ以上は問いがぼやけるので絞る
- 「この意思決定のポイント」は **フェーズ6完了時のみ** 出す。新規に追加された `decisions[]` エントリ全件について、`why`/`why_not` を **業務文脈で再現できる 1 文** に要約（DML 側にも同じ文を `options[].why`/`why_not` で保存）

### 構造化テーブルの書き方

- 列: `レーン (BC)` / 各種別カラム（Actor / Command / Policy / Event）
- 行: 時系列ステップごとに 1 行（同じ BC が複数回出現してもよい）
- 該当しない種別セルは `—`
- 非同期遷移は最後尾セルに `⚡` を付与
- カラム順は固定: `🟨 Actor → 🟦 Command → 🟪 Policy → 🟧 Event`
- Read Model がある場合は `🟩 Read Model` カラムを Actor の後ろに挿入

## 4. 「往復 vs 完了」の判定基準

assistant が自己判断する。

### 完了と判定するシグナル

- ユーザーが明示: 「OK」「いいね」「次へ」「進めて」「合意」「確定」「これでいい」
- 該当フェーズの主要項目が揃っている:
  - フェーズ1: ドメイン / ゴール / 主要アクター
  - フェーズ2: ストーリー 400-600字 + 代替シナリオ 2-3本
  - フェーズ3: 10-20件のイベント候補
  - フェーズ4: 各 EVT に CMD と Actor が紐付き、非同期遷移が同定
  - フェーズ4.5: LANGUAGE が記録され、レーン境界が明確
  - **フェーズ4.6: 全 AGG エントリの `aggregates[].purpose`（30字以上）が記入され、`background`/`constraints[]` の有無を判定**
  - フェーズ5: 全 AGG の不変条件・エラー、`brs` 分岐、**`aggregates[].attrs[]` / `aggregates[].events[].params[]` の確定**。各 `rules[].why`、各 `errs[].when` の記入率を確認
  - **フェーズ6: 主要な設計判断が `decisions[]` に記録され、各 option に `why`/`why_not` が記述されている**
  - フェーズ7: causal-check 完了、残課題レビュー済

### 往復と判定するシグナル

- ユーザーから修正・追加・質問が出ている
- `?` シグナル受領
- 「もうちょっと議論したい」「ここをもう一度」
- ユーザーが沈黙して assistant が次の問いを出すターン (合意取得前)

### 迷ったら往復扱い

完了テンプレは HTML 生成のコストが高いので、判定が曖昧なら往復として処理する。次ターン以降で完了シグナルが出たらまとめて完了出力する。

## 5. DML 抜粋の粒度

| タイミング | 抜粋範囲 |
|---|---|
| フェーズ内往復 | 原則出さない。例外: SCENARIO 1つが大きく書き直されてユーザー確認が必要なときのみ末尾に 1 件 |
| フェーズ1完了 | DML はまだ出さない (CONTEXT 名すら確定していない) |
| フェーズ2完了 | `contexts` のみ (up / dn 含む) |
| フェーズ3完了 | 新規追加された scenario の `name` / `actor` / `evt` のみ (cmd/rules は未確定) |
| フェーズ4完了 | 該当フェーズで追加・確定した scenario 全文 (cmd/evt/agg/rules 入り) |
| フェーズ4.5完了 | `lang` + `contexts` の追加分 |
| **フェーズ4.6完了** | **トップレベル `aggregates[]` の新規エントリ（`name`/`ctx`/`purpose`/`background`/`constraints`/`states`）と `contexts[].aggs` 名簿の追加分のみ。加えて「### AGG 目的・背景・制約サマリ」テーブルで各 AGG の `purpose` 1 行と制約件数を 1 表で示す** |
| フェーズ5完了 | 新規 rules/errs が追加された scenario 全文 + policies 要素 (新規分) + `aggregates[].transitions[]`/`attrs[]`/`events[].params[]` の追加分。`rules[].why`、`errs[].when` がある分は併記 |
| **フェーズ6完了（意思決定ログ）** | **新規 `decisions[]` エントリ（id/topic/chosen/options[]）。各 option の `why`/`why_not` を 1〜2 行で簡潔に報告** |
| フェーズ7完了 | **新規分の抜粋のみ + MD/HTML ファイルパスを案内**。DML 全文は別ファイル `<session>.dml.yaml` に保持、チャットには流さない |

DML 抜粋は ` ```dml ` コードブロックで囲む。

## 6. HTML 更新粒度

| フェーズ | HTML 操作 |
|---|---|
| 1. スコープ | HTML はまだ作らない |
| 2. ストーリー | `.dml.yaml` を **Write で新規作成**（`narratives[]` に `kind: happy`/`alt` を並べる）+ `Bash open` で初回起動。HTML §1 ストーリー + 進捗バー入り |
| 3. イベント発見 | `.dml.yaml` を **Edit で `scenarios[]` の仮 entries ＋ `contexts[].lang` に新規識別子追加**。HTML §2 はビルダーが自動再生成（`entry` 付き narratives が無ければプレースホルダ） |
| 4. CMD-EVT-POLICY | `.dml.yaml` を **Edit で `scenarios`（`next`/`brs[].terminal` を含む）/`policies`/`narratives[].entry`（happy + 代替 1〜2）追加 ＋ `contexts[].lang` 更新**（HTML 用語集セクションは廃止済み） |
| 4.5. BC 境界 | `.dml.yaml` を **Edit で `lang` 追加**。HTML §6 はビルダーが自動再生成 |
| 4.6. 目的・背景・制約 | `.dml.yaml` を **Edit で `aggregates[]` に `purpose`/`background`/`constraints` 追加** |
| 5. RULE-ERR + 属性・イベントペイロード | `.dml.yaml` を **Edit で `scenarios[].rules`/`errs` + `aggregates[].attrs`/`events[].params` を追加**。HTML §7 はビルダーが自動再生成 |
| 6. 意思決定ログ | `.dml.yaml` を **Edit で `decisions[]` 追加**。HTML §5 はビルダーが自動再生成 |
| 7. 整合性チェック | HTML を **Edit で全セクション最終化**（実際の Edit は `.md`/`.dml.yaml` 側） |

HTML は MD と並行して常に最新状態を保つ。`open` で起動した外部ブラウザは `<meta http-equiv="refresh">` で 3 秒ごとに自動リロードして反映される。

**Claude Code preview panel は meta-refresh を実行しない** ため、フェーズ完了時にチャット応答の最後で `Read dist/eventstorming/<session>.html` を必ず呼び、preview panel に最新版を表示する。これで内蔵プレビュー・外部ブラウザの両方で最新状態が見られる。HTML は数千行になるので、この `Read` は `limit` 付き（冒頭 数十行）で可 — 目的は preview 反映のトリガーであり、全文をコンテキストに載せる必要はない。

## 7. ホットスポット / 未確認事項の管理

- 番号はセッション通じて **通し番号** (H1, H2, ..., Q1, Q2, ...)
- 解決済みは欠番、再利用しない
- フェーズ完了テンプレでは **そのフェーズで追加・更新・解決があった項目** だけを出す
- フェーズ内往復テンプレでは **そのターンで追加・更新があった項目** だけを差分表示

## 8. 編集インタラクション

ユーザーが自然言語で図を編集できる。assistant は指示を解釈して MD ファイルと HTML に反映する。

### 8-1. ユーザーの指示パターン

| 言い方 | 解釈 | 反映先 |
|---|---|---|
| 「E3 を"招待送信済"に変えて」 | EVT のラベル変更 | DML の `evt` リネーム（scenarios/policies 全箇所）＋ `contexts[].lang` の該当キー更新。フロー連鎖は scenarios.name で繋がっているので EVT 名変更の影響なし。HTML §2 はビルダーが自動再生成 |
| 「主催者BCに Admin を追加」 | レーンへの actor 追加 | 該当 scenario に `actor: Admin` ＋ 所属 BC の `contexts[].lang` に `Admin: "管理者"` 追加。HTML はビルダーが自動再生成 |
| 「C2 と E2 の間に メール送信 を挟んで」 | CMD 挿入 | 新 scenario を追加 + 前後 scenario の `next` を再配線（中継 scenario を挟む） |
| 「E4 を消して」 | 削除 | DML から該当 `evt` 削除 + 影響を受ける scenario の brs / policies[].trg を再点検。下流に影響あれば `[?]` 警告 |
| 「P1 を notifications BC に動かして」 | POLICY 移動 | policy の `ctx` を変更。policy は scenarios[].evt → policies[].trg で自動挿入されるため明示的な参照修正は不要。HTML §2 のレーン分割はビルダーが自動再生成 |
| 「Member BC を participant にリネーム」 | CONTEXT リネーム | `contexts[].name` を member → participant に変更し scenarios/policies/aggregates の `ctx` 参照も更新 |
| 「ハッピーパスをやり直したい」 | フェーズ2 へロールバック | `narratives[]`（`kind: happy`/`alt`）を再構築 + `narratives[].entry` と `scenarios[].next` を組み直し |

### 8-2. assistant の反映手順 (1指示あたり)

1. ユーザー指示を **対象アイテム** (A1/C2/E3 や日本語ラベル) と **操作** (追加/削除/変更/移動/リネーム) に分解
2. **テキストで確認**: 「`E3 = 参加申し込みが完了した` を `招待送信済` に変更し、DML の `evt: ParticipationApplied` を `evt: InvitationSent` にリネームします。OK?」
3. ユーザー OK → `.dml.yaml`（DML）を `Edit`（`contexts[].lang` 含む）で一貫して更新
4. HTML は触らない（ビルダーが自動再生成）
5. 品質チェックサブエージェント (`quality-check-agent.md`) を起動（`.md` ＋ 兄弟 `.dml.yaml` を対象。HTML は対象外）
6. **フェーズ完了相当の変更なら** チャット本文に構造化テーブル付き完了メッセージ。**細かい変更なら** テキスト確認のみ

### 8-3. 複数同時指示

「3つ変えたい」と言われたら、全部リストアップして 1 回の `Edit` で MD を書き換え、HTML も 1 回の Edit で更新、品質チェックは 1 回起動。

## 9. フォールバックモード (HTML 生成不可の環境)

書き込み権限がない、サンドボックスで `Bash open` が効かない等の状況なら、HTML を作らずチャット本文のテーブルのみで運用する。

ユーザーへの通知例:
```
HTML ファイルが生成できないため、以降は構造化テーブルのみで Event Flow を表示します。
書き込み権限が復活したら教えてください。
```

## 10A. WHY 補完モード（H-WHY ホットスポット）

quality-check で **S8 違反**（AGG `#### 目的` 未記入 / 30 字未満）または **W1/W2 違反**（RULE の `WHY` 不足 / ERR の `WHEN` 不足）が検出されたら、ファシリテーター本体が次ターンの応答末尾に **`### WHY 補完が必要`** セクションを置き、優先度（目的 > 制約 > WHY > WHEN）で **1 件ずつ** ユーザーに問う。

### テンプレート

```markdown
### WHY 補完が必要

- **H{n}** ({種別}): {問いかけ文}

例) この AGG が「単一の責任主体」として担う責務を 1 文で言語化してください。
「何をするか（CMD で表現済み）」ではなく「なぜこの単位で切るか」を書いてください。
```

ユーザー回答 → 該当 MD/DML を `Edit` → quality-check を再走 → クローズ。複数の `H-WHY` が同時にある場合は **1 ターン 1 件** に絞る（質問は 1 回に 1 つの原則を維持）。ユーザーが `？` を返したら判断軸（例: 「責任の核 / 業務的価値 / 実装が直接守る制約」）を 2〜3 点提示する。

### `H-WHY` の表記

既存の `H{n}. [?]` 形式に並ぶ新種別。番号は通し（H1, H2, ... と同じ列）で、ラベルに `[?-WHY]` プレフィックスを付けて区別する：

```markdown
### ホットスポット
- H5. [?] capacity の責務は Event / Participation どちらか
- H6. [?-WHY] AGG `Payment` の `#### 目的` 未記入 — 決済責務の核を 1 文で言語化が必要
- H7. [?-WHY] rule `participation must be in APPLIED status` の `why` 未記入
```

クローズ済みは欠番、再利用しない（既存運用と同じ）。

## 10B. `？` シグナルの段階対応

ユーザーが送る全角 `？` は「判断に迷った・決めきれない」の合図。**同一論点で連続して届いた回数**に応じて対応を変える。狙いは、推測で埋めず（SKILL.md ① 会話プロトコル）かつセッションを止めないこと。1〜2 回目でユーザーの判断を助け、それでも決まらない 3 回目は「Claude とユーザーだけでは決めきれない論点」と認めて有識者へ委ね、記録を残して前へ進む。**3 回目では、ユーザーが有識者にそのまま口に出せる具体的な質問文を 1 つ渡す**のが肝（抽象的に「確認してください」で終わらせない）。

このセクションは `？` を**受けた後の振る舞い**を規定するもので、末尾の「迷ったら `？`」案内の頻度（§10）とは別物。

### 段階の定義

| 回 | 振る舞い |
|----|---------|
| 1 回目 | 判断の軸を 2〜3 点提示（押しつけない） |
| 2 回目 | 角度を変える — 比喩・対比・小さな表で噛み砕く（§噛み砕きパターン: `references/term-glossary.md`）、または仮候補を 1 つ添えて反応を見る |
| 3 回目 | **エスカレーション**（下記 3 点をこの順で） |

**カウントの数え方**: いま議論している論点（該当する `H{n}`/`Q{n}`）を会話履歴から追い、同一論点で連続した `？` を数える。論点が解決するか別の論点に移ったらリセット（セッション通算ではない）。

### 3 回目のエスカレーション（順に実行）

1. **有識者へ「そのまま聞ける質問文」を 1 つ用意する（このステップの核）** — 「有識者に確認するのが確実です」と勧めて終わらせない。**ユーザーが有識者に会ったときコピペでそのまま口に出せる、業務の言葉で書いた具体的な問い**を `> ❓ **有識者への質問**:` の引用行として必ず出す。"何を聞けばこの論点が一意に決まるか" を質問文として言い切る。良い質問の 3 条件：
   - **(a) Claude ではなく有識者に向いた二人称** — 「〜ですか？」と有識者に直接尋ねる形。「〜を確認してください」という Claude → ユーザーへの指示文で終わらせない。
   - **(b) 業務の言葉だけで書く** — DDD／専門用語（CORE / SAME-TX / 集約 など）を質問文に混ぜない。有識者は業務のプロであって DDD のプロではない。
   - **(c) 答えが返れば論点が一意に決まる粒度** — できれば Yes/No か二択を引き出す。曖昧な「どう思いますか？」は不可。
2. **記録** — 論点を `questions[]` に open で追加。chat の 未確認事項 `Q{n}` 番号と id を揃える。`note` 冒頭に `[有識者相談推奨]` を付け、**用意した質問文も `note` に含めておく**（有識者確認時にそのまま再利用できる）：
   ```
   dmlctl add <session>.dml.yaml --to=questions \
     --item='{id: Q3, topic: "<迷っている論点>", why: "<なぜ確信が持てないか>", status: open, note: "[有識者相談推奨] 有識者への質問: <そのまま聞ける問い>。仮置き: <暫定結論>"}'
   ```
3. **仮置き確認** — 仮置きのリコメンドを 1 つ提示し、「これで仮置きして進めますか？」の問いで終わる。同意されたら仮の値で進めるが、**`questions[]` エントリは open のまま残す**（後続フェーズ／次回セッションで再評価）。同意されなければ保留のまま次へ。

**質問文の良し悪し（build BC を CORE/SUPPORTING どちらにするか迷った例）**：

| | 質問文 |
|---|---|
| ❌ 悪い（勧めるだけ・抽象・DDD 用語） | 「DR/FAT の目利きが CORE サブドメインかどうか有識者に確認してください」 |
| ✅ 良い（そのまま聞ける・業務語・二択を引き出す） | 「設計審査や工場立会い検査で見つける不備は、チェックリスト通りにやれば他部門や他社でも同じように見つかるものですか？ それとも、うちの設備技術だからこそ気づける勘所がありますか？」 |

### 3 回目の出力テンプレート

```markdown
（本文: これまでの往復で決めきれない点を 1〜2 文で言語化）

この論点は Claude とユーザーだけで確定するのは難しそうです。**業務の有識者（ドメインエキスパート）にこう聞いてみてください**：

> ❓ **有識者への質問**: <業務の言葉で書いた、そのまま口に出せる具体的な問い。DDD 用語を使わず、Yes/No か二択で答えが返る粒度>

この問いの答えが返れば論点が決まります。忘れないよう未確認事項として記録しました（Q{n}、open）。

いったん前に進めるために、仮置きのリコメンドを 1 つ置きます：

> 💡 仮置き: <暫定の結論> — 理由: <1 行>

これで仮置きして進めますか？（有識者の回答が出たら Q{n} を見直します）
```

「おまかせ」シグナル（SKILL.md）とは区別する。「おまかせ」は Claude がデフォルトを黙って選んで進める合図で、有識者相談の勧めも記録も伴わない。

## 10. 出力の節約原則

- 1 メッセージが iOS で 3-4 スクロール以上にならないようにする
- 同じ情報を繰り返さない (フェーズ完了時の DML 抜粋は新規分のみ、全文は別ファイル `<session>.dml.yaml`)
- 💡 ポイント解説は**セッション中で初出の時 1 回だけ**。同じ用語を再度解説しない（チャット履歴のテキスト検索で既出判定）
- 「迷ったら `？`」案内は毎ターン繰り返さない (フェーズ完了時 + 初回のみ)
- 「保存しました」「再起動します」のような実装的なメッセージは出さない
- フェーズ完了マーク `✅` は使ってよい (進捗が見える)
- HTML ファイルパス案内は **相対パス** で書く（`docs/eventstorming/...`）、Markdown リンク `[file.html](path)` 形式
